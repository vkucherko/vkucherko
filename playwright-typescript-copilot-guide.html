01

The big pictureHow the three pieces fit together

Three tools, three jobs

Everything we do sits on three layers that each answer a different question:

  • Playwright — the engine that drives a real browser (and makes API calls). It clicks, types, navigates, and checks what the page shows. It answers "does the app actually work?"
  • TypeScript — the language we write the tests in. It's JavaScript with type-checking, so mistakes get caught as you type instead of at runtime. It answers "is this test written correctly?"
  • GitHub Copilot — the AI assistant inside our editor (VS Code). It suggests code, drafts tests from a comment, explains unfamiliar lines, and can even drive the browser to explore. It answers "can I write this faster?"
Say it like this

Playwright is the robot that uses the app. TypeScript is the language we give the robot its instructions in. Copilot is the assistant that helps us write those instructions.

Where UI and API testing sit

Playwright does both, with the same syntax and the same runner:

  • UI testing — drive the browser like a user: open a page, fill a form, click a button, check the result on screen.
  • API testing — call the backend directly over HTTP: send a request, check the status code and the JSON that comes back. No browser needed.

The real power is combining them: use a fast API call to set up data, then verify it in the UI. More on that in section 10.

The one mental model that explains most of Playwright

Why it matters

Playwright waits automatically. When you tell it to click a button, it waits for that button to exist, be visible, and be ready — then clicks. You almost never add manual pauses. Half of "flaky test" problems in older tools disappear because of this. Keep this in mind and the rest of the guide clicks into place.

Project anatomy & running testsWhat the files are and how to run them

What a project looks like

A typical Playwright + TypeScript repo has a predictable shape:

my-app/
├─ tests/                  # our test files (*.spec.ts)
│  ├─ login.spec.ts
│  └─ checkout.spec.ts
├─ pages/                  # Page Objects (reusable helpers) — see §11
├─ playwright.config.ts    # central config: browsers, base URL, timeouts
├─ package.json            # scripts + dependencies
└─ playwright/.auth/       # saved login state (git-ignored) — see §9

The config file is the control room

playwright.config.ts is where shared settings live, so individual tests stay clean:

import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  use: {
    baseURL: 'https://staging.our-app.com', // so tests say '/login', not the full URL
    trace: 'on-first-retry',                 // capture a debug trace when a test retries
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox',  use: { ...devices['Desktop Firefox'] } },
  ],
});
Say it like this

Set things once here — which browsers, the base web address, how long to wait — and every test inherits them.

Running the tests

A handful of commands cover day-to-day work:

npx playwright test                 # run everything (headless = no visible browser)
npx playwright test login.spec.ts   # run just one file
npx playwright test --headed        # watch it happen in a real browser
npx playwright test --ui            # open UI Mode: the best way to run + debug
npx playwright show-report          # open the HTML report after a run
✓ Good practice

UI Mode (--ui) is the one to demo. It shows every step, lets you time-travel through a test, and re-runs on save. It makes the whole thing tangible.

03

Anatomy of a testHow a test is actually created

The shape of every test

A test is a named block with three moves: Arrange (get set up), Act (do the thing), Assert (check the result).

import { test, expect } from '@playwright/test';

test('user can log in', async ({ page }) => {
  // Arrange — go to the page
  await page.goto('/login');

  // Act — do what a user would do
  await page.getByLabel('Email').fill('ada@example.com');
  await page.getByLabel('Password').fill('correct-horse');
  await page.getByRole('button', { name: 'Sign in' }).click();

  // Assert — check what should now be true
  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
});

The parts, named

  • test('name', ...) — declares one test; the name shows up in reports.
  • async / await — browser actions take time, so we await each one. If you forget await, the test races ahead and behaves oddly — it's the most common beginner bug.
  • { page } — a fixture: a fresh, isolated browser tab handed to the test automatically. Each test gets its own, so tests never contaminate each other.
  • expect(...) — the assertion. If it fails, the test fails.
Say it like this

Every test reads like a little script: go here, do these steps, then confirm you see what you expected. The await in front just means "wait for this to finish before the next line."

Grouping and shared setup

Related tests go in a describe block, and repeated setup goes in a hook so you don't copy-paste it:

test.describe('Checkout', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/cart');          // runs before every test in this group
  });

  test('shows the subtotal', async ({ page }) => { /* ... */ });
  test('applies a coupon',   async ({ page }) => { /* ... */ });
});

Hooks: beforeEach / afterEach run around each test; beforeAll / afterAll run once for the whole group.

With Copilot Drafting a test from a sentence

With Copilot

// Test: a logged-out user visiting /account is redirected to /login

Copilot fills in the goto, the action, and the assertion. You then read it, fix the locators to match our real app, and confirm it fails when the feature is broken. Draft with Copilot, verify with your own eyes.

04

Locators — finding things on the pageThe single most important skill

What a locator is

A locator is a description of an element — "the button that says Sign in." It's how a test points at things before clicking or checking them. Get locators right and tests stay solid; get them wrong and tests break every time a developer tweaks the markup.

Why it matters

A locator is lazy: it doesn't grab the element immediately, it re-finds it each time you use it, waiting until it's there. That's what makes Playwright tests resilient without manual pauses.

The priority ladder — reach for these in order

Prefer the way a human identifies an element (its role, its label, its text) over how the code is built (CSS classes, IDs). Top of the ladder = fewer broken tests.

// 1. By role + accessible name — the default, use this ~80% of the time
await page.getByRole('button', { name: 'Sign in' }).click();
await page.getByRole('link',   { name: 'Sign up' }).click();
await page.getByRole('checkbox', { name: 'Remember me' }).check();

// 2. By form label — best for inputs
await page.getByLabel('Password').fill('secret123');

// 3. By placeholder — when there's no proper label
await page.getByPlaceholder('Enter your email').fill('a@b.com');

// 4. By visible text — for non-interactive content
await expect(page.getByText('Welcome back, Ada')).toBeVisible();

// 5. By test id — an explicit hook devs add: data-testid="submit"
await page.getByTestId('submit').click();

// LAST RESORT: CSS / XPath — brittle, avoid when you can
await page.locator('.btn-primary').click();
✓ Good practice

Teams that moved from XPath/CSS to getByRole report dramatically fewer flaky tests. If an element has no good role or label, the right fix is usually to add one in the app — that also makes the product more accessible. Two wins from one change.

The full locator toolbox

The ladder above is the short version. Here is every built-in locator, roughly best-to-last, so you can match the tool to the element:

  • getByRole(role, { name }) — ARIA role plus accessible name; the default for anything interactive. Options sharpen it: { exact }, { level } for headings, { checked }, { expanded }, { pressed }.
  • getByLabel(text) — a form field by its associated label. The first choice for inputs.
  • getByPlaceholder(text) — inputs that show placeholder text instead of a label.
  • getByText(text) — non-interactive content by visible text (substring by default; pass { exact: true } for the whole string).
  • getByAltText(text) — images and other elements carrying an alt attribute.
  • getByTitle(text) — elements with a title attribute (tooltips).
  • getByTestId(id) — a data-testid hook. An escape hatch, not the default (see below).
  • page.locator(css) — a raw CSS selector; fine for a structural wrapper that has no meaningful role.
  • page.locator('xpath=…') — XPath; genuine last resort, brittle, and never for interactive elements.
  • page.frameLocator(sel) — step into an iframe before locating inside it.
  • Shadow DOM is handled for you: the getBy* locators pierce open shadow roots automatically (closed ones are inaccessible by design).
// images and tooltips
await expect(page.getByAltText('Company logo')).toBeVisible();
await page.getByTitle('Close dialog').click();

// inside an iframe
const frame = page.frameLocator('#payment');
await frame.getByLabel('Card number').fill('4242 4242 4242 4242');

// a raw CSS wrapper with no useful role — fine as a scope, then locate by role inside it
const card = page.locator('.product-card').filter({ hasText: 'Keyboard' });
await card.getByRole('button', { name: 'Add to cart' }).click();
Why it matters

Every rung down the ladder trades a little resilience for a little reach. getByTestId verifies that a test id exists — not that the UI is accessible or that a user can actually operate it — so it earns its place as a fallback, not a habit.

Under the hood

getByRole resolves against the browser's accessibility tree — matching the ARIA role plus the computed accessible name (assembled from the label, aria-label, aria-labelledby, and text). That's why it tracks what a user perceives rather than DOM structure. A locator is a lazy query, not a captured handle: it re-resolves on every use, so it can't go stale across re-renders. Sharpen matches with options like { exact: true } or { level: 2 } for headings, and compose with .and(), .or(), and .filter({ hasText }).

Narrowing down: chaining & filtering

When a page has many similar elements, scope the search instead of guessing:

// Chain: find the button inside a specific card
await page.getByRole('listitem')
          .filter({ hasText: 'Wireless Mouse' })
          .getByRole('button', { name: 'Add to cart' })
          .click();

// Pick by position (0-based) when order is meaningful
await page.getByRole('row').nth(2).click();
await page.getByRole('row').first();
await page.getByRole('row').last();
✗ Pitfall

If a locator matches several elements, Playwright throws a "strict mode" error on purpose. Don't silence it with .first() — that hides real ambiguity and clicks whatever happens to be first. Scope the locator more precisely instead.

Different ways to write the same locator

Once you have picked a type, several dials tune precision. Knowing them keeps you out of brittle, index-based selectors:

// Exact vs substring name (default is substring, case-insensitive)
page.getByRole('button', { name: 'Save' });               // matches "Save changes"
page.getByRole('button', { name: 'Save', exact: true });  // only "Save"

// Regex name — dynamic or partial text
page.getByRole('heading', { name: /order #\d+/i });

// Filter a set by its text, or by a child it contains
page.getByRole('row').filter({ hasText: 'MacBook Pro' });
page.getByRole('row').filter({ hasNotText: 'Sold out' });
page.getByRole('listitem').filter({ has: page.getByRole('button', { name: 'Remove' }) });

// Combine conditions (1.42+)
page.getByRole('button').and(page.getByTitle('Subscribe'));
page.getByLabel('Country').or(page.getByPlaceholder('Country'));

// Scope to a region instead of searching the whole page
const dialog = page.getByRole('dialog', { name: 'Confirm delete' });
await dialog.getByRole('button', { name: 'Yes' }).click();
✓ Good practice

Reach for hasText / has and region scoping before nth(). Index-based locators like nth(2) or first() encode the current layout and break when order changes — use them only when position is the thing you actually mean ("the first row").

When the good locators aren't there

Sometimes the markup gives you nothing to hold onto — CSS-in-JS hashes class names on every build, IDs are regenerated, or (increasingly in 2026) an AI coding agent rewrote a component overnight. Work down this list:

  • Add the semantics in the app — a role, a real label, or an aria-label. Best fix: the test gets a stable hook and the product gets more accessible.
  • Add a data-testid on the specific element if you can't change its semantics — an explicit contract that survives refactors.
  • Point Playwright at your attribute if the team uses a different name: use: { testIdAttribute: 'data-test' }.
  • Only then fall to a scoped CSS locator — keep it shallow (one stable ancestor plus a role), never a long descendant chain.
Under the hood

"Self-healing" locators — where an AI re-identifies an element when the primary locator misses — are a real 2026 trend and can cut selector-maintenance churn sharply. Treat them as a safety net over good locators, not a replacement: a healed locator still needs review, or the suite quietly drifts away from what it was meant to check.

With Copilot Let the tool pick the locator

With Copilot

Two ways to get good locators without hand-writing them:

  • npx playwright codegen <url> — records your clicks and writes the locators for you, already following the priority ladder. Great for discovery.
  • Copilot autocomplete will suggest getByRole(...) as you type. But always sanity-check the name it invents — AI (and codegen) can grab a fragile locator. Section 13 covers this.
05

AssertionsChecking that the app did the right thing

Assertions wait, too

Playwright's expect on a locator auto-retries for a couple of seconds until the condition is true or it times out. So you check for the end state without worrying about exact timing.

await expect(page.getByRole('heading')).toHaveText('Dashboard');
await expect(page.getByText('Saved')).toBeVisible();
await expect(page.getByRole('button', { name: 'Submit' })).toBeEnabled();
await expect(page.getByRole('listitem')).toHaveCount(3);
await expect(page).toHaveURL(/.*\/dashboard/);
await expect(page.getByRole('checkbox')).toBeChecked();
Say it like this

An assertion is the "did it work?" line. And it's patient — it keeps checking for a moment, so we don't have to hard-code how long the app takes.

The assertion catalog

Web-first assertions all take expect(locator) and auto-retry until they pass or time out. The ones you'll reach for, grouped:

// Visibility & existence
await expect(loc).toBeVisible();
await expect(loc).toBeHidden();
await expect(loc).toHaveCount(3);

// State
await expect(loc).toBeEnabled();
await expect(loc).toBeDisabled();
await expect(loc).toBeChecked();
await expect(loc).toBeEditable();
await expect(loc).toBeFocused();

// Text & value
await expect(loc).toHaveText('Order placed');   // exact (or pass an array for many)
await expect(loc).toContainText('placed');       // substring
await expect(loc).toHaveValue('a@b.com');
await expect(loc).toBeEmpty();

// Attributes & classes
await expect(loc).toHaveAttribute('href', '/login');
await expect(loc).toHaveClass(/active/);

// Page-level
await expect(page).toHaveURL(/\/dashboard/);
await expect(page).toHaveTitle('Dashboard');

// Negation — put .not before the matcher
await expect(loc).not.toBeVisible();

// Visual — pixel snapshot compared to a stored baseline
await expect(page).toHaveScreenshot('dashboard.png');
✓ Good practice

Assert the outcome a user would notice — text appeared, the URL changed, the count went to 3 — not an implementation detail. And prefer one precise assertion over a screenshot where you can: screenshots catch everything, including intended changes, so they're noisy as a default and best reserved for genuinely visual checks.

Soft assertions — check several things, fail once

By default a failed assertion stops the test. A soft assertion records the failure but keeps going, so one run surfaces every problem:

await expect.soft(page.getByTestId('name')).toHaveText('Ada');
await expect.soft(page.getByTestId('role')).toHaveText('Engineer');
// test continues even if the first one failed — both get reported
Under the hood

Web-first assertions (expect(locator)) poll the DOM until the condition holds or the expect timeout elapses — 5s by default, and separate from the action timeout. For arbitrary conditions, expect.poll(() => fn()) and await expect(fn).toPass() retry the same way; tune them with expect.configure({ timeout, intervals }). This poll-and-retry model is exactly why you assert the end state and never sleep.

Two flavors, don't mix them up

Why it matters

expect(locator).toBeVisible() retries. expect(value).toBe(5) — a plain value like a number or string — does not retry; it checks once. Use locator assertions for anything the page renders, and value assertions for data you already have in hand.

Actions & interactionsClicking, typing, and everything a user does

The common actions

await page.getByRole('button', { name: 'Save' }).click();
await page.getByLabel('Search').fill('playwright');        // clears then types
await page.getByLabel('Bio').pressSequentially('slow', { delay: 100 }); // key-by-key
await page.getByLabel('Agree').check();                    // checkbox / radio
await page.getByLabel('Country').selectOption('Canada');   // dropdown
await page.getByRole('button', { name: 'Menu' }).hover();
await page.getByLabel('Avatar').setInputFiles('photo.png'); // file upload
await page.keyboard.press('Enter');
✓ Good practice

Use fill() for normal typing — it's instant and reliable. Only reach for pressSequentially() when you specifically need to trigger per-keystroke behavior (like an autocomplete that reacts to each letter).

Beyond click and fill — the fuller set

The full range of user actions, all called on a locator and all auto-waiting for actionability first:

// Click variants
await loc.click();
await loc.dblclick();
await loc.click({ button: 'right' });              // context menu
await loc.click({ modifiers: ['Shift'] });         // shift-click
await loc.click({ position: { x: 4, y: 4 } });     // a precise point

// Text input
await loc.fill('hello');                           // set value instantly (the default)
await loc.pressSequentially('hi', { delay: 50 });  // key-by-key (autocomplete)
await loc.press('Enter');                          // one key or chord: 'Control+A'
await loc.clear();

// Choices
await loc.check();  await loc.uncheck();
await loc.setChecked(true);
await loc.selectOption('US');                      // a <select>; or { label }, or an array

// Files, hover, focus, drag, scroll
await loc.setInputFiles('invoice.pdf');            // upload (pass [] to clear)
await loc.hover();
await loc.focus();  await loc.blur();
await loc.dragTo(page.getByTestId('trash'));
await loc.scrollIntoViewIfNeeded();

// Low-level, when a widget needs it
await page.keyboard.press('Escape');
await page.mouse.move(100, 200);
✓ Good practice

For a real OS file dialog you can't script, wait for the chooser event instead of clicking blind: page.on('filechooser', fc => fc.setFiles('a.png')), then trigger the button.

Actions check first — "actionability"

Why it matters

Before clicking, Playwright confirms the element is visible, stable (not animating), enabled, and not covered by something else. If a modal is fading in, it waits for it to settle. This is why you rarely need manual waits before an action.

07

Waiting: do's & don'tsThe topic that fixes the most flaky tests

Rule one: don't sleep

✗ Pitfall

await page.waitForTimeout(3000) — a fixed sleep — is the classic mistake. It's slow when the app is fast and still flaky when the app is slow. Waiting for an outcome is both faster and more reliable.

// DON'T: guess a duration
await page.getByRole('button', { name: 'Load' }).click();
await page.waitForTimeout(3000);              // ✗ hope 3s is enough

// DO: wait for the thing you actually expect
await page.getByRole('button', { name: 'Load' }).click();
await expect(page.getByText('Results ready')).toBeVisible();  // ✓
Under the hood

Before an action, Playwright runs an ordered actionability gate: attached → visible → stable (same bounding box across two animation frames) → receives events (a hit-test at the action point confirms nothing covers it) → enabled — retrying the whole set until the action timeout. waitForLoadState('networkidle') is discouraged for apps with polling or websockets, because "idle" may never arrive; wait on a specific response or a visible outcome instead.

The explicit-wait toolkit — wait for a signal

When auto-waiting isn't enough — a background request, a URL change, a specific DOM condition — wait on the real event, never on a timer:

// A network response (e.g. the save call), started before the click that triggers it
const saved = page.waitForResponse(r => r.url().includes('/api/save') && r.ok());
await page.getByRole('button', { name: 'Save' }).click();
await saved;

// A navigation / URL change
await page.waitForURL('**/dashboard');

// A page lifecycle state (prefer 'load'/'domcontentloaded'; avoid 'networkidle' on polling apps)
await page.waitForLoadState('domcontentloaded');

// An arbitrary DOM/JS condition in the page
await page.waitForFunction(() => document.querySelectorAll('.row').length > 10);

// A specific locator reaching a state, explicitly
await page.getByRole('alert').waitFor({ state: 'visible' });

// Poll a value or an API until it settles (retries are built in)
await expect.poll(async () => (await api.get('/status')).status()).toBe(200);
await expect(async () => { await expect(loc).toHaveText('Done'); }).toPass();
✗ Pitfall

waitForTimeout is the escape hatch of last resort — fine for a throwaway local spike, never in a committed test. If you think you need it, there is almost always a response, a URL, or an element state to wait for instead.

When you do need to wait explicitly

Most waiting is automatic. For the rest, wait for a real signal:

// Wait for a specific network response (e.g. after clicking Save)
await page.waitForResponse(resp => resp.url().includes('/api/orders'));

// Wait for navigation / network to settle
await page.waitForLoadState('networkidle');

// Poll a custom condition until it passes (with built-in retry + timeout)
await expect(async () => {
  const res = await request.get('/status');
  expect(res.status()).toBe(200);
}).toPass();
Say it like this

Instead of "wait three seconds and hope," we say "wait until the results appear" or "wait until the server answers." It waits exactly as long as needed — no more, no less.

08

Loops & iterationWhich loop, and where to use it

The golden rule: use for…of, avoid forEach

✗ Pitfall

array.forEach(async …) does not wait for the await inside it. The loop finishes instantly while the actions are still running — a subtle, painful bug. Use for…of, which respects await.

const items = ['Apple', 'Pear', 'Plum'];

// ✗ WRONG — forEach ignores await; steps overlap and race
items.forEach(async (name) => {
  await page.getByLabel(name).check();
});

// ✓ RIGHT — for...of runs one step, waits, then the next
for (const name of items) {
  await page.getByLabel(name).check();
}
Under the hood

array.forEach(async …) invokes every callback synchronously and throws away the promises they return — so the await inside never pauses the loop and any rejection goes unhandled; the loop reports "done" before the async work is. for … of suspends the async function at each await (true sequential order). await Promise.all(items.map(fn)) starts them concurrently and settles together — throughput when order doesn't matter, though one rejection rejects the whole batch.

When you want them in parallel

Sequential (for…of) is the safe default. When actions are independent and order doesn't matter, fire them together with Promise.all:

// Run several independent checks at once
await Promise.all([
  expect(page.getByTestId('name')).toHaveText('Ada'),
  expect(page.getByTestId('email')).toBeVisible(),
  expect(page.getByRole('button', { name: 'Edit' })).toBeEnabled(),
]);
✓ Good practice

Sequential when one step depends on the last, or when clicking things changes shared state. Parallel only for independent reads/assertions. When in doubt, sequential.

Looping over elements on the page

To act on every matching element, get them all with .all(), or count and index:

// Cleanest: iterate the resolved list
const rows = page.getByRole('row');
for (const row of await rows.all()) {
  await expect(row).toBeVisible();
}

// Or by index when you need the number
const count = await rows.count();
for (let i = 0; i < count; i++) {
  await expect(rows.nth(i)).toContainText('$');
}

The most useful loop of all: data-driven tests

Loop over a list of data to generate a separate test per case. One block, many tests, each reported on its own:

const logins = [
  { role: 'admin',  landing: 'Admin Console' },
  { role: 'editor', landing: 'Content' },
  { role: 'viewer', landing: 'Dashboard' },
];

for (const { role, landing } of logins) {
  test(`${role} lands on the right page`, async ({ page }) => {
    await page.goto(`/login?role=${role}`);
    await expect(page.getByRole('heading', { name: landing })).toBeVisible();
  });
}
Say it like this

Instead of copy-pasting the same test three times with different data, we list the data and let a loop stamp out one test for each row. Add a case? Add a line.

09

Session storage & auth reuseLog in once, reuse it everywhere

The problem it solves

If every test logged in through the UI, a 200-test suite would log in 200 times — slow and pointless. Instead, we log in once, save the resulting session (cookies + local/session storage) to a file, and hand that file to every other test so they start already signed in.

Why it matters

Playwright calls this saved session storageState. It captures exactly what the browser remembers about your logged-in session — the tokens and stored values that keep you authenticated.

Step 1 — a setup test that logs in and saves state

// auth.setup.ts
import { test as setup, expect } from '@playwright/test';

const authFile = 'playwright/.auth/user.json';

setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('ada@example.com');
  await page.getByLabel('Password').fill('correct-horse');
  await page.getByRole('button', { name: 'Sign in' }).click();
  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();

  // Save cookies + storage to a file
  await page.context().storageState({ path: authFile });
});

Step 2 — wire it up so it runs first, then reuse

// playwright.config.ts
projects: [
  { name: 'setup', testMatch: /auth\.setup\.ts/ },
  {
    name: 'chromium',
    use: {
      ...devices['Desktop Chrome'],
      storageState: 'playwright/.auth/user.json', // start signed in
    },
    dependencies: ['setup'],   // run 'setup' before this project
  },
],

Now every test in chromium opens already logged in. No login steps cluttering your tests.

✗ Pitfall

That auth file contains real session tokens. Add playwright/.auth to .gitignore — never commit it. Treat it like a password.

Say it like this

One test logs in and saves the "signed-in" state to a file. Every other test loads that file and skips straight to the real work. It's the single biggest speed-up in the suite.

Beyond one login — the patterns you'll need

The setup-project trick scales to the real cases:

  • Multiple roles — run one setup test per role, each saving its own file (admin.json, user.json), then choose per project or per test.
  • API-based login — skip the login screen entirely: POST credentials with the request context and save the returned session. Setup is fast and not hostage to a flaky login form.
  • Two users at once — open a second context with another saved session in the same test to check interactions between accounts (chat, sharing, permissions).
  • Deliberately logged out — for tests that must start signed out, use an empty state: storageState: { cookies: [], origins: [] }.
  • Token expiry — if sessions are short-lived, re-run setup (it's a dependency) or refresh inside a worker-scoped fixture so each worker stays authenticated.
// pick a saved session per test
test.use({ storageState: 'admin.json' });

// or bring a second logged-in user into one test
const userB = await browser.newContext({ storageState: 'userB.json' });
const pageB = await userB.newPage();
✓ Good practice

Log in once per role, reuse it everywhere, and never script the login form inside a feature test — it's slow and it couples every test to your auth UI.

Same runner, no browser

Playwright hands tests a request fixture for making HTTP calls. You check the status code and the JSON body — no page, no clicking.

import { test, expect } from '@playwright/test';

test('GET /users returns a list', async ({ request }) => {
  const response = await request.get('/api/users');

  expect(response.ok()).toBeTruthy();      // status 200–299
  expect(response.status()).toBe(200);

  const body = await response.json();
  expect(body).toHaveLength(10);
  expect(body[0]).toHaveProperty('email');
});

Sending data — POST, PUT, DELETE

test('creates a todo', async ({ request }) => {
  const response = await request.post('/api/todos', {
    data: { title: 'Buy milk', done: false },
    headers: { Authorization: 'Bearer token123' },

  const created = await response.json();
  expect(created.title).toBe('Buy milk');

Under the hood

The request fixture is an APIRequestContext with its own cookie jar and baseURL, fully independent of any browser. Hand a browser the same session by piping request.storageState() into browser.newContext({ storageState }) — that's how an API login seeds a UI test. Responses are lazy: call .json() or .body() to read them, and large payloads can be streamed rather than buffered.

The power move: API sets up, UI verifies

Use a fast API call to create data, then check it appears correctly in the interface. Faster and less flaky than clicking through setup:

test('a new todo shows in the list', async ({ request, page }) => {
  // Arrange via API (instant)
  await request.post('/api/todos', { data: { title: 'Ship release' } });

  // Verify via UI
  await page.goto('/todos');
  await expect(page.getByText('Ship release')).toBeVisible();
});
Say it like this

Two ways to talk to the app: through the screen like a user, or straight to the server like another program. Often we set the stage the fast way — a direct server call — then confirm the user actually sees the result on screen.

Asserting responses & the fuller request set

The request context does far more than GET/POST, and its responses carry their own assertions — no browser involved:

// Response assertions

await expect(res).toBeOK();                 // any 2xx
expect(res.status()).toBe(200);
const body = await res.json();

await request.post('/api/login', {
  headers: { 'Content-Type': 'application/json' },
  data: { user: 'ada', pass: 'secret' },

// Set base URL / default headers / auth once, in config:
// use: { baseURL, extraHTTPHeaders: { Authorization: `Bearer ${token}` } }
✓ Good practice

Two high-value patterns: seed via API, verify in the UI (fast, reliable setup), and cover pure API contracts — status, shape, error codes — as their own tests that run in milliseconds with no browser.

Structure at scaleKeeping a big suite maintainable

Page Object Model — one place per page

Instead of repeating locators across dozens of tests, gather a page's elements and actions into a class. When the UI changes, you fix it in one file.

// pages/LoginPage.ts
import { type Page } from '@playwright/test';

export class LoginPage {
  constructor(private page: Page) {}

  async goto() {
    await this.page.goto('/login');
  }

  async login(email: string, password: string) {
    await this.page.getByLabel('Email').fill(email);
    await this.page.getByLabel('Password').fill(password);
    await this.page.getByRole('button', { name: 'Sign in' }).click();
  }
}
// the test becomes readable and change-proof
test('login', async ({ page }) => {
  const login = new LoginPage(page);
  await login.goto();
  await login.login('ada@example.com', 'correct-horse');
  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
});
Say it like this

We describe each screen once — its fields and what you can do on it — and tests just call those actions. If a button gets renamed, we update one file, not fifty tests.

Tags & isolation — a couple of habits

  • Tag tests to run subsets: test('checkout @smoke', …), then npx playwright test --grep @smoke.
  • Keep tests independent. Each should set up its own data and not rely on another test having run first. Playwright isolates browser state per test by default — lean into it.
✓ Good practice

A test you can run alone and in any order is a test you can trust. Shared state between tests is the root of most "it only fails in CI" mysteries.

Past page objects — components, fixtures & data

A page object is the start. Three patterns keep a large suite clean as it grows:

  • Component objects — model a reusable widget (a nav bar, a date picker, a data grid) once and compose it into page objects, instead of duplicating its locators on every page that shows it.
  • Page objects as fixtures — hand each page object to tests through a custom fixture, so a test receives a ready loginPage just by naming it — no new LoginPage(page) boilerplate.
  • Test-data factories — generate unique, valid data per test (a fresh email, an order with random items) from a small helper, so tests never collide and never depend on a fixed row existing.
// A page object exposed as a fixture
export const test = base.extend<{ loginPage: LoginPage }>({
  loginPage: async ({ page }, use) => { await use(new LoginPage(page)); },
});

// tests just ask for it
test('sign in', async ({ loginPage }) => {
  await loginPage.signIn('ada@corp.com', 'secret');
});

// a tiny factory keeps every test independent
const user = makeUser();   // { email: 'ada+8f3@corp.com', name: 'Ada L.' }
Say it like this

A page object holds locators and actions, a fixture holds setup and lifecycle, and a factory holds data. Keep those three jobs separate and the suite stays easy to change.

Debugging & toolingFinding out why a test failed

The four tools worth knowing

  • UI Mode — npx playwright test --ui. Watch each step, time-travel through the run, re-run on save. The everyday driver.
  • Trace Viewer — a recorded timeline of a failed run: DOM snapshots, network, console, screenshots at every step. Open a saved trace with npx playwright show-trace trace.zip. Turn traces on with trace: 'on-first-retry' in config so CI failures come with a full replay.
  • Codegen — npx playwright codegen <url>. Records your actions into ready-made test code; also a fast way to discover good locators.
  • VS Code extension — run and debug tests from the editor, set breakpoints, and pick locators by pointing at the page.

Evidence on failure & running in CI

Configure Playwright to capture screenshots and video only when something breaks, and it slots straight into GitHub Actions / Jenkins / Azure DevOps:

// playwright.config.ts
use: {
  screenshot: 'only-on-failure',
  video: 'retain-on-failure',
  trace: 'on-first-retry',
},
retries: process.env.CI ? 2 : 0,   // retry flaky tests in CI, not locally
reporter: [['html'], ['list']],    // a browsable report + live console output
Say it like this

When a test fails in the pipeline, we don't guess. We open the trace and literally watch the failure play back, step by step, with the network and screenshots attached.

More debugging levers

Beyond the four tools, a few switches earn their keep:

  • Pause & step — drop await page.pause() to open the Inspector at that line, or run with --debug (PWDEBUG=1) to step the whole test and pick locators live.
  • Re-run only what failed — --last-failed after a red run; --repeat-each=20 to smoke out a flaky test; --grep @smoke to scope by tag.
  • Headed & serial — --headed to watch a real browser, plus --workers=1 when a race only shows up when tests run one at a time.
  • The HTML report — npx playwright show-report opens the last run with traces attached; it's the first thing to open on a CI failure.
✓ Good practice

When a test flakes, reach for the Trace Viewer first. It replays the exact run — DOM, network, console, screenshots — so you diagnose from evidence instead of re-running and hoping.

What Copilot actually does for testing

Copilot lives inside VS Code — no separate tool, no context switch. For Playwright work, it helps in a few concrete ways:

  • Comment → code — write a plain-English comment describing a scenario, and it drafts the test.

Chat, and switching models

This is the newest and most powerful piece. With Copilot

The guardrails — this is the important part

✗ Pitfall

A test that always passes is worse than no test — it's a green checkbox giving false confidence. AI happily writes tests that never actually exercise the feature. ✗ Pitfall

AI agents tend to click the first thing that roughly matches even when several similar elements exist, and silently skip steps that depend on state they didn't notice. ✓ Good practice

The workflow that works: Copilot drafts → you read every line → you run it and watch it fail when it should → you commit. Copilot is a fast junior pair, not an oracle. Our judgment is still the product.

Copilot gets us to a first draft in seconds. Our job shifts from typing to reviewing — making sure the test actually catches a real break. That reviewing skill is exactly what keeps us valuable.

Agents & the agentic loopWhat "agentic AI" actually means

Assistant vs agent — the one distinction that matters

An AI assistant suggests and hands back to you — Copilot completing a line, a chatbot answering a question. An AI agent takes a goal and works it across multiple steps on its own: it plans, uses tools, checks the result, and keeps going until the goal is met or it hits a limit you set. Anthropic's way of putting the building block: an agent is "a language model enhanced with tools, retrieval, and memory."

Say it like this

An assistant hands you a suggestion and waits. An agent takes a goal and works the problem — trying, checking, and adjusting — until it's done or it hits a limit we set.

Why it matters

The difference is consequences. An agent can take real actions — open a pull request, drive a browser, update a Jira ticket, run the test suite. That's powerful, and it's why guardrails matter more for agents than for a chatbot that only talks.

The agentic loop — this is the "loop" people mean by AI

Under the hood, almost every agent runs the same repeating cycle, often called ReAct (Reason + Act). It reasons about the goal, acts by calling a tool, observes the result, and loops — using each result to decide the next step, so it can catch its own mistakes and adjust.

        ┌─────────────────────────────────────────────┐
        │                                             │
        ▼                                             │
   PERCEIVE / REASON  →  PLAN  →  ACT (call a tool)  →  OBSERVE the result
        │                                             │
        │        keep looping, adapting each time     │
        └──────────────────► until a clear STOP ──────┘
              (goal met, or a limit / step-cap is hit)
Why it matters

This is a different "loop" from the for…of loops in section 08 — those iterate over data in a test; this is how an AI iterates toward a goal. Because each action's result feeds back in, a good agent self-corrects: if a search returns junk, it reasons about why and tries a better query.

✓ Do

  • Set a max-iteration cap and a clear stopping condition
  • Keep a human in the loop for risky actions
  • Give it a specific goal and success criteria
  • Log every step so you can trace what it did

✗ Don't

  • Let it run uncapped — agents burn roughly 4× the tokens (more in multi-agent), so a loop that should take 5 steps and takes 20 is slow and costly
  • Hand it a vague goal — vague prompts, vague behaviour
  • Let it take production actions with no review

How you set one up (in plain terms)

You don't hand-code the loop. You configure three things, and a framework runs the loop for you:

  • A job description — a system prompt naming the agent's role, goal, constraints, and when to stop or escalate.
  • Tools it may use — each with a precise name and description, because the agent reads those to decide when to reach for it.
  • Guardrails — a step cap, human approval for sensitive actions, and logging.

Frameworks like Claude's tool-use API, LangGraph, CrewAI, or the OpenAI Agents SDK differ in packaging, but the three ideas above are the same everywhere.

Say it like this

You're not writing the loop by hand — you're writing the agent's job description, handing it the right tools, and setting the limits it has to stay inside.

✗ Pitfall

The two most common failures are a vague goal and poorly described tools. If a tool's description is fuzzy, the agent picks the wrong one at the wrong time — the reasoning is only as good as what you gave it to reason with.

Under the hood

Mechanically the loop is just a growing message history: the model emits a tool call, the runtime executes it and appends the result to the conversation, and the model is invoked again on the larger context — repeating until it emits a final answer or hits a step cap. Reflection/Reflexion variants add a self-critique turn; orchestrator-worker setups spawn specialised sub-agents (Anthropic's research system reported roughly 90% gains over a single agent on internal evals). Because the whole context lives in a bounded window, long runs need summarisation or retrieval to stay in budget.

In QA Where agents show up in our work

The Playwright MCP agent from section 13 is exactly this pattern: given "write a test for the checkout flow," it drives a real browser, inspects the page, and generates the test. Agents also draft first-pass tests, self-heal scripts when the UI shifts, triage failures, and explore edge cases. The next two sections cover what powers them (skills, MCP, RAG) and how to use them without losing quality.

Interview angle

"How do you use AI agents in testing, and how do you keep them reliable?" A strong answer names the split: agents draft and maintain; humans own the risk calls and verify every result. That judgment is exactly what stays valuable.

Patterns: from simple chains to full agents

"Agent" covers a spectrum. Most production systems are really a workflow — a fixed, predictable path — and reserve a fully autonomous agent for the few tasks that genuinely need one. The common patterns, simplest first:

  • Prompt chaining — fixed steps, each feeding the next (draft → refine → format). Predictable and cheap; use when the steps are known.
  • Routing — a classifier sends the input down the right branch (bug vs feature request; simple vs complex). Use when inputs fall into clear categories.
  • Parallelization — run subtasks at once and combine (check a change against ten rules simultaneously), or vote across several runs for reliability.
  • Orchestrator–workers — a lead model splits a task into sub-tasks, delegates to workers, then synthesizes (Anthropic's research system uses this). For open-ended work whose shape isn't known up front.
  • Evaluator–optimizer — one model produces, another critiques, loop until it passes. When you have clear quality criteria and iteration helps.
  • Autonomous agent — the model plans, acts, and self-corrects in an open loop until done. Highest ceiling, highest cost and risk; use only when the path truly can't be pre-defined, always with guardrails.
✓ Good practice

Match the pattern to the task and climb this list only when a simpler rung falls short. A fixed workflow you can trace beats an autonomous agent you can't — reserve autonomy for the problems that actually need it.

Skills, MCP & RAGThe three things that make an AI useful on our work

On its own, an agent only knows general things and can only talk. Three pieces change that: skills teach it how we do a task, MCP plugs it into our tools, and RAG feeds it our knowledge.

Skills — packaged know-how

A skill is a folder with a short instruction file (a SKILL.md) that teaches the AI how to do one specific task the way your team wants — plus any helper scripts it needs. The AI reads the skill's description and pulls the skill in on its own when it's relevant.

How one is made: write a SKILL.md with a name, a description (this is what tells the AI when to use it — say both what it does and when to trigger), then the step-by-step instructions. Optionally bundle templates or scripts. Then test it on real prompts and refine.

---
name: raise-bug-our-format
description: Write a bug report in our team's format. Use whenever someone reports a
  defect, pastes an error, or asks to "log a bug" — even if they don't say "bug report".
---

# Raise a bug (our format)

1. One-line summary: what's broken, and where.
2. Steps to reproduce, then expected vs actual.
3. Environment (browser, build) and severity.
4. Link the failing test or trace if there is one.
Say it like this

A skill is a recipe card we hand the AI so it does a task our way, every time — a house-style test, a bug in our format, a review against our checklist.

✓ Do

  • Make the description specific — what it does and when to use it
  • Keep each skill small and single-purpose
  • Version skills in git; test them on real cases

✗ Don't

  • Stuff everything into one giant skill
  • Leave a vague description — the AI won't know to use it
  • Bake secrets or credentials into a skill file

MCP — the universal adapter to our tools

The Model Context Protocol is an open standard that lets an AI connect to outside tools and data through one common interface — think "USB-C for AI." Before MCP, every tool needed its own custom integration; with MCP, a tool exposes an MCP server once and any MCP-capable AI can use it.

Why it matters

Anthropic introduced MCP in late 2024 and, in December 2025, handed it to the Linux Foundation's Agentic AI Foundation — so it's now vendor-neutral, backed by OpenAI, Google, Microsoft, AWS and others, with 500-plus public servers. Your AI is the client; it connects to a server for each tool. The Playwright MCP server from section 13 is one of these — it's what lets the AI drive a real browser to generate valid locators.

In our daily QA life: with the right servers connected, the AI can read and create Jira tickets, open GitHub pull requests, query the test database, and drive the browser — all without anyone writing custom glue for each.

✓ Do

  • Use trusted, authenticated servers
  • Grant least privilege — only the access it needs
  • Review what each server is allowed to do

✗ Don't

  • Connect unvetted public servers to sensitive systems — 2025 scans found thousands of public MCP servers with no authentication
  • Give a server broad write access to production without guardrails

RAG — giving the AI our knowledge

Retrieval-Augmented Generation means the AI doesn't answer only from what it learned in training. First it retrieves relevant documents from a knowledge base you control, then it answers grounded in them — so answers are current, specific to your system, can cite their source, and hallucinate far less.

Say it like this

A great doctor from memory is good. A doctor who also pulls up your latest test results before advising is better. RAG is that second layer — real, current, our-own information.

How it works, plainly: your documents are split into chunks and indexed in a searchable store; a question fetches the most relevant chunks; those are handed to the model along with the question. In QA: point it at your requirements, acceptance criteria, past bug reports, and test cases, then ask "has this been tested?", "generate tests from this feature's acceptance criteria," or "is this new bug a duplicate?" — grounded in our system, not the generic web.

✓ Do

  • Curate the knowledge base — quality in, quality out
  • Keep it current; retire stale docs
  • Respect access controls on what it can read

✗ Don't

  • Feed it stale or contradictory docs
  • Assume RAG ends hallucination — it reduces it; still verify
  • Ingest data the AI shouldn't be able to see
Under the hood

RAG retrieval is vector similarity: documents are embedded into high-dimensional vectors, the question is embedded the same way, and the store returns the nearest chunks by cosine similarity — chunk size and overlap are the main quality levers, and graph or "agentic" RAG (several retrieval rounds) handle multi-hop questions. MCP itself is JSON-RPC over stdio or HTTP: a server advertises its tools, resources, and prompts, and the client discovers them when it connects.

The RAG family — pick by your failure mode

"RAG" isn't one design; it's a ladder. Start simple and climb only when your results fall short:

  • Naive / standard RAG — retrieve the top chunks by vector similarity, then answer. Great for simple Q&A over clean docs (an internal FAQ, a single requirements doc); brittle on compound or jargon-heavy questions.
  • Hybrid retrieval + reranking — combine keyword search (BM25) with vector search, then re-score the top candidates for precision. The cheapest big win and the production default; reach for it the moment you see misses on exact ticket IDs, error codes, or API names.
  • Query transformation (incl. HyDE) — rewrite or split the question, or embed a hypothetical answer instead of the raw query. For vague, multi-part questions that don't map to any single chunk.
  • Graph RAG — represent documents as an entity-relationship graph and traverse it. For relationship and traceability questions across documents ("which tests cover this requirement," "which requirements touch this module").
  • Corrective / Self-RAG — the model grades its own retrieval and re-searches (or falls back to web) when the evidence is weak. When a wrong answer is genuinely costly — anything feeding a release decision.
  • Agentic RAG — an agent plans, retrieves, checks whether it has enough, and re-retrieves in a loop. Highest quality but slow and expensive; reserve for complex, multi-hop triage a single pass can't handle.
Say it like this

Don't pick RAG by novelty — pick it by what's failing. Missing exact terms? Add hybrid search and a reranker this week. Only reach for graphs or agents when the simpler rungs demonstrably aren't enough.

✓ Good practice

For us: naive over a requirements doc answers "is this covered?"; hybrid + rerank nails lookups by bug ID or error code; graph RAG powers traceability between tests and requirements; agentic RAG handles "given this failure, pull the related bug, the requirement, and the last passing run."

How the three fit together

Say it like this

A modern QA agent uses all three at once: it pulls the acceptance criteria (RAG), follows our test-writing skill (skill), drives the browser through the Playwright server and opens a pull request through the GitHub server (MCP) — then we review what it produced.

What an MCP server actually offers

Under the standard, a server exposes three kinds of things, and the client discovers them when it connects:

  • Tools — actions the AI can call (open a PR, run a query, drive the browser). These do things.
  • Resources — read-only data the AI can pull in (a file, a record, a doc). These inform.
  • Prompts — reusable prompt templates the server offers for common tasks.

Transport is JSON-RPC over stdio (a local process) or HTTP (a remote service) — that's the whole surface, which is exactly why one Playwright MCP server works in Copilot, Cursor, Claude, or any other MCP client. And because a server can expose powerful tools, connect only trusted, authenticated ones and grant the least access that does the job.

AI in your QA workflowUsing it well — and the guardrails that keep quality

What AI is genuinely good at in QA today

The parts that are production-ready right now are the repetitive ones: first-draft test authoring, self-healing maintenance (auto-updating scripts when a UI element or API shifts), test-data generation, failure triage and summarizing, predictive "where bugs are likely" analysis, and risk-based test selection. It's also great at explaining unfamiliar code or a failing test.

Say it like this

AI clears the repetitive work — first drafts, maintenance, test data, triage — so we spend our time on the judgment calls it can't make.

What stays human

Risk decisions, coverage strategy, exploratory testing, domain knowledge, and final sign-off stay with people. The job shifts from writing every test to writing the quality objectives the AI works against — success criteria, risk thresholds, coverage priorities — and then reviewing what it produces. The old goal of "maximize coverage" is giving way to "maximize risk coverage."

Why it matters

Industry data in 2026 is blunt about it: a majority of AI-generated code needs human intervention, and unreviewed AI output is one of the top sources of flaky suites — around half of QA leaders using AI name maintenance and flaky scripts as their main challenge. The reviewing is the safeguard, not an optional extra.

The golden rule: AI output is a first draft

Everything AI writes gets a human review before it enters the suite — and you confirm each generated test actually fails when the feature breaks. A test that only ever passes is proving nothing.

✗ Pitfall

Because AI makes it trivial to generate thousands of test cases, the temptation is to keep them all. Don't. A pile of low-value tests slows the pipeline, inflates maintenance, and buries the real failures in noise. Point the effort at high-risk, high-traffic, business-critical flows.

A simple, safe way to use AI day-to-day

Give the AI real context and ask for a draft you'll review — don't ask it to invent from thin air:

Here are the acceptance criteria: [paste them]
Here's how we write tests — Page Object Model, getByRole locators: [link the file]
Draft a Playwright test for the "expired card" case. I'll review it before it merges.

Put shared rules in a team conventions file (the .github/copilot-instructions.md from section 13) so everyone's AI follows the same house style and guardrails.

✓ Do

  • Review every generated test before it merges
  • Give the AI context — criteria, existing code, conventions
  • Use it for maintenance, triage, and first drafts
  • Keep humans on risk, strategy, and sign-off
  • Keep tests in your repo to avoid vendor lock-in
  • Confirm each test can fail when it should

  • Ship AI code unread

  • Assume the AI knows our domain — it doesn't
Under the hood

The new testing surface is non-determinism — the same prompt can produce different output run to run — so you validate behaviour with evals (graded example sets) and tolerance-based checks rather than exact-match assertions. Lowering the model's temperature reduces variance but never removes it, which is why a human still owns the final call on AI-generated tests.

Where it's heading — so we're not caught out

The direction is agentic: agents that plan, generate, and maintain tests against goals you set; self-healing suites; and risk-based orchestration that puts effort where it matters. Test artifacts are increasingly read by agents too, so writing them clearly pays off twice. The durable skill isn't operating any one tool — it's defining what quality means and governing what the AI produces.

Say it like this

The teams that win aren't the ones with the fanciest tools — they're the ones who got clear about what quality means and kept people owning that call.

How a QA engineer thinks in 2026From a feature landing to the ticket closing

A feature lands in your queue. What separates a thoughtful senior QA engineer from a test-runner isn't which tools they reach for — it's how they think at each step. In 2026 the rote work (drafting cases, executing, summarising failures) is increasingly done by AI, which moves the human's time up the chain to the parts that always needed judgment: risk, strategy, exploration, and owning the call to ship.

Here is the whole arc, from a feature arriving to the ticket closing, and how each step is approached now.

Say it like this

A senior QA isn't the person who runs the tests — they're the person who can answer "what could go wrong, how likely is it, how bad would it be, and are we OK shipping anyway?" Every step below serves that one question.

1 · Understand the feature before a single test exists

Read the ticket and acceptance criteria, then hunt for what isn't written down. Who uses this? What does it touch? What does "done" and "correct" actually mean here? The senior move is to surface the ambiguity early — in refinement, while it's still cheap — not after the code is built. This is shift-left: quality starts at design, not at the end of the sprint.

✓ Good practice

The best bugs are prevented, not found. A sharp question in refinement — "what happens if the payment succeeds but the callback times out?" — is worth more than a dozen tests written afterwards. In 2026 you can have AI pull the related past bugs and requirements so you arrive informed, but the questions are yours to ask.

2 · Assess the risk — decide what actually matters

You can't test everything, and trying is how suites become slow and pointless. Map where a failure would hurt most: business-critical paths, high-traffic areas, the parts that just changed, and the parts with a bad history. Risk is likelihood times impact, and it sets the priority for every step that follows. This is the shift the whole field made — from maximising test coverage to maximising risk coverage.

Say it like this

The question isn't "did we test everything?" It's "did we test the things that would hurt us most if they broke?" Deciding that is the scarce skill now that AI can generate tests in seconds — producing tests is cheap; knowing which ones are worth having is not.

3 · Plan the approach — the right test at the right layer

Decide the mix before writing anything: what to check at the unit and API layers (fast, stable) versus the few end-to-end journeys that genuinely need a browser; what to automate versus explore by hand; the data and environments you'll need; and what is explicitly out of scope. Define the exit criteria — what "tested" means for this feature — up front. Increasingly, that up-front definition of quality objectives is the senior's main artifact; the automation and the AI work against it.

✓ Good practice

Push logic checks down to the API layer where they run in milliseconds and rarely flake; reserve slow end-to-end tests for the handful of journeys a user would actually notice breaking. A plan that respects the test pyramid is what keeps a suite fast at scale.

4 · Design the cases — think like a user and an adversary

Turn the criteria and risks into concrete cases: the happy path, the boundaries, the negative and error paths, the strange inputs, accessibility, and the failure modes nobody wrote down. Hold two hats at once — the user trying to succeed and the adversary trying to break it.

✗ Pitfall

Let AI draft the obvious cases from the acceptance criteria — then do the senior work: prune the low-value ones and add the edge cases it won't imagine. AI is strong on the cases you'd have written anyway and blind to the ones that matter — the race condition, the half-finished payment, the expired token. Those are yours.

5 · Automate — but treat AI's output as a first draft

Build the automated checks at the layer you chose, in the team's conventions — Page Object Model, stable role-based locators. Every test an AI or codegen produces gets read before it merges, and you confirm it actually fails when the feature breaks. Cheap generation is a trap: don't let it flood the suite with low-value tests that slow every run and hide the real failures.

✓ Good practice

A test that has never failed is not proven to work. Break the thing on purpose once and watch the test go red — only then do you trust it. This one habit catches the most dangerous AI failure: a test that passes but was quietly checking the wrong thing.

6 · Explore — where the real bugs still hide

Scripted checks confirm what you expected; exploratory testing finds what you didn't. Time-boxed, charter-based sessions poking at the unexpected paths are more valuable than ever precisely because AI now handles the rote checks. Does it feel right? What happens if I do this out of order, twice, on a slow connection? This is human judgment at its highest leverage.

Say it like this

Automation checks the things we thought of. Exploration finds the things we didn't — and that is still, firmly, a person's job.

7 · Run and triage — read a failure like a detective

Run locally and in CI, then read a red result critically: is it a real bug, a flaky test, a bug in the test itself, or an environment problem? Reproduce it, isolate it, and gather evidence — the trace, the logs, the video. In 2026 AI can cluster and triage failures and draft repro steps, which is a real time-saver, but you verify before you trust and before you cry wolf.

✓ Good practice

A failing test is a question, not a verdict. Telling a genuine defect from a flaky test from an environment blip — quickly, and without raising false alarms — is one of the clearest markers of a senior.

8 · Report defects that actually get fixed

A good bug report is one clear line on what's broken, exact steps to reproduce, expected versus actual, the environment, evidence attached, and an honest severity tied to real risk. AI can draft it in your house format from a skill — you make sure the severity and the risk framing are right, because that's what drives whether it gets prioritised.

Say it like this

Severity isn't how annoyed you are — it's how much this hurts the user and the business. Frame the bug in those terms and it lands at the top of the queue instead of the bottom.

9 · Verify the fix and guard against regression

Confirm the fix does what it should, confirm it didn't break the neighbours, and add a regression test so this exact bug can't quietly return. Re-run the tests the change actually touches — risk-based selection — rather than blindly re-running everything.

✓ Good practice

Every bug you close should leave behind a test that would have caught it. That's how a suite gets smarter over time instead of just bigger — and it's how field failures, once found, stop coming back.

10 · Gate, sign off, and own the call

The pipeline enforces the objective gates — tests green, thresholds met, no open criticals. The senior adds the judgment on top: given what we tested and what we deliberately didn't, and the residual risk, are we comfortable shipping? That call, and communicating it plainly, is the part of the job AI can't take — accountability for quality still sits with a human.

Say it like this

Green tests are an input, not the decision. The decision is "are we OK shipping this, knowing what we know?" — and saying that out loud, with the known gaps named, is the senior's job.

11 · Close it out — then watch production

Mark it done with a trail: what was tested, what wasn't, and the known risks. Then shift-right — watch the feature in the real world through monitoring, error rates, and real-user signals, because some bugs only appear at scale. Feed what you learn back into the risk model and turn any field failure into a new regression test.

✓ Good practice

Closing the ticket isn't the finish line. A feature is truly "done" when it's behaving in production and you've folded whatever you learned back into how you test the next one. Quality in 2026 is a loop, not a checkpoint.

What stays constant, and what's new in 2026

Constant: curiosity, risk thinking, the habit of viewing a system as both a user and an adversary, clear communication, and ownership of the ship decision. New: AI absorbs the rote drafting, maintenance, and triage, so a QA engineer's time moves up to risk, strategy, exploration, and judgment. The people who thrive aren't the fastest test-writers — they're the clearest thinkers about quality and risk.

Interview angle

This whole arc is the senior QA interview. They rarely ask "what's the syntax for a Playwright locator"; they ask "walk me through how you'd approach testing this feature." A strong answer is exactly this: risk first, the right test at the right layer, review the AI's work, explore what it can't, and own the call to ship.

Under the hood

The industry frames this shift as "script author → quality owner," and the reason is structural: AI erased the speed penalty of writing tests by hand while leaving risk judgment — the senior skill — completely untouched. Maturity models for autonomous testing say the same thing: as automation rises, human roles move from maintenance to strategic oversight, defect review, and quality guidance. That's the work that grows in value.

Playwright vs SeleniumWhat changed, and why teams moved

The one-sentence version

Selenium talks to the browser through a translator, over the network. Playwright talks to the browser directly. Almost everything else — the speed, the lower flakiness, the built-in waiting — follows from that one difference.

Selenium:    script → WebDriver client → driver binary → browser     (an HTTP request per command)
Playwright:  script ───────────────────────────────────→ browser     (one persistent WebSocket, browser's own protocol)
Say it like this

Selenium sends each command as a separate message through a driver in the middle. Playwright keeps one live line open straight to the browser. Fewer hops, less waiting, fewer things to break.

Why it matters

Selenium uses the W3C WebDriver protocol: every action is an HTTP round-trip to a driver binary (ChromeDriver, GeckoDriver) that relays it to the browser. Playwright speaks the browser's own debugging protocol — CDP for Chromium, patched equivalents for Firefox and WebKit — over a single WebSocket that stays open, so the browser can push events back without being polled. That open channel is the root of both the speed and the auto-waiting. Independent 2026 benchmarks put Playwright roughly 20–42% faster with markedly fewer flaky tests, though on remote cloud grids network latency dominates and the gap narrows.

Side by side

 PlaywrightSelenium

WaitingAuto-waits on actionability by defaultYou write the waits yourself (explicit / implicit)
Browser enginesChromium, Firefox, WebKit — bundledVery wide, including legacy browsers; drivers managed per browser
LanguagesJS/TS (first-class), Python, Java, .NETJava, Python, C#, JS, Ruby — broader footprint

Under the hood

WebDriver Classic is request/response over HTTP — one round-trip per command, the historical source of latency and race conditions. BiDi adds a persistent WebSocket so the browser can push events (network, console, DOM mutations) without polling; Selenium is migrating its implementation from Classic to BiDi, with the high-level API arriving in Selenium 5. So the gap is closing at the transport layer even though the default developer experience still differs.

The honest trade-offs — where Selenium still wins

A senior answer never trashes the other tool. Selenium is older, standardized, and still the right call in real situations:

  • Language and browser reach — Ruby support, very mature Java/C#, and coverage of legacy browsers Playwright doesn't target.
  • Selenium Grid at scale — for large distributed, on-premise infrastructure across data centres, Grid (now Docker- and Kubernetes-native) is hard to beat.
  • W3C standard — being a vendor-neutral standard rather than one company's tool matters to some regulated organizations.
  • Existing investment — a large, working Selenium suite is expensive to rewrite; migration has to earn its cost.
✓ Good practice

Frame it as fit, not "better": choose Playwright for new projects, WebKit/Safari coverage, built-in network mocking and API testing, and TS/JS teams; choose Selenium when you have a large existing suite, need Ruby or legacy-browser coverage, or run distributed Grid on-prem. Knowing both, and when each fits, is the senior signal.

Interview angle

Selenium hasn't stood still: WebDriver BiDi adds a bidirectional, WebSocket-based layer that brings Selenium native network interception and real-time console/log capture it used to lack, and Selenium 4.x exposes CDP hooks too. The high-level BiDi API is still landing (fuller in Selenium 5). A strong answer: "BiDi is genuinely narrowing the gap — but the default experience still differs. Playwright waits for elements out of the box; Selenium still asks you to write the waits, which is where a lot of its flakiness comes from." Naming BiDi at all signals you follow the space.

Stacking the tools: Postman & API testingWhere Postman, Newman, and Playwright's request client each fit

Two tools, two jobs — not rivals

Postman is an API client and collaboration platform: build collections of requests, manage environments, stand up mock servers, do contract testing, and run it all in CI. Playwright's request fixture is a code-first HTTP client that lives in the same project as your browser tests. The "Postman vs Playwright" debate dissolves once you see them as complementary layers.

Say it like this

Postman is where we explore and share APIs. Playwright's request client is where API checks live right next to our UI tests — same repo, same run, same report.

Postman + Newman in the pipeline

Teams author requests visually in Postman, add assertions in the Tests tab, then run the collection in CI with Newman, Postman's command-line runner:

npx newman run orders.postman_collection.json \
  -e staging.postman_environment.json \
  --reporters cli,junit --reporter-junit-export results.xml
✓ Good practice

This is the best on-ramp for a mixed team: product managers and manual testers can build and run API checks without writing a test project. Newman's JUnit output drops straight into the same pipeline tab your Playwright results use.

Playwright's request fixture — the co-location payoff

Because the request client shares cookies, auth state, and baseURL with the browser context, one test can move between the API and the UI. The strongest pattern: set up state through the API, verify it through the UI — fast and reliable to arrange, real user path to check.

test('order shows up after API seed', async ({ page, request }) => {
  // Arrange — create the order straight through the API (fast, deterministic)
  const res = await request.post('/api/orders', { data: { sku: 'ABC-123', qty: 2 } });
  expect(res.ok()).toBeTruthy();
  const { id } = await res.json();

  // Act + Assert — verify it the way a user would see it
  await page.goto(`/orders/${id}`);
  await expect(page.getByRole('heading', { name: 'Order ABC-123' })).toBeVisible();

  // Cross-check the backend state via the API again
  const check = await request.get(`/api/orders/${id}`);
  expect((await check.json()).status).toBe('confirmed');
});
Why it matters

One runner, one config, one report, one set of CI secrets — for both API and UI. A Newman-only test can't share the browser's auth session or interleave with UI steps, so it can't do this seed-then-drive trick.

Under the hood

The two clients differ in state, not just syntax: Newman drives a Postman collection as an isolated process with its own environment, while APIRequestContext shares a cookie jar, baseURL, and storageState with the browser context in the same run. That shared state is precisely what lets a Playwright test authenticate through the API and then continue as the same user in the UI — something a Newman run structurally cannot do.

Interview "Postman or Playwright for API testing?"

Interview angle

They're checking for false-dichotomy thinking. Strong answer: Postman for fast exploration, shareable collections, mock servers, contract tests, and low-code teams; Playwright's request client for version-controlled, maintainable regression that shares state and CI with the E2E suite. "Most serious teams run both — Postman to explore, Playwright to regress." Then mention the maintenance cost of running two pipelines: two fixture systems, two env setups, two secret stores — so co-locate API checks with E2E when it pays off.

✗ Pitfall

Don't over-migrate for its own sake. A large existing Postman collection with pre-request scripts against a non-JS backend can be costly to port. Move what benefits from co-location; leave exploration and cross-team collaboration in Postman.

CI/CD pipelinesRunning the suite on every change — Azure Pipelines & GitHub Actions

What a pipeline is for

CI is the robot that runs the whole test suite on every push, so a broken change is caught before it reaches anyone. Every pipeline, whatever the tool, is the same five stages:

  • Trigger — on push and on pull request
  • Install — Node, dependencies, and the browsers
  • Run — execute the tests
  • Collect — publish results and the report as artifacts
  • Gate — a failing run blocks the merge
Say it like this

Tests only protect us if they run by themselves on every change. A suite that only runs on someone's laptop protects no one.

The non-negotiables in CI

  • Set CI=true — Playwright reads it and adjusts behaviour (and won't try to pop open a report on a headless agent).
  • Install browsers with npx playwright install --with-deps so the OS libraries are present too.
  • Record trace, screenshot, and video on failure only — full-run recording burns storage for no benefit.
  • Publish JUnit for the pipeline's test tab and the HTML report as an artifact for humans.
  • Allow a couple of retries in CI for transient failures — but treat a retried test as a bug to investigate, not a fix.
  • Shard across runners once the suite is slow.
✗ Pitfall

The classic "green pipeline, empty report." The reporter array must include html, and CI must be set so Playwright doesn't try to launch a browser to open it. Configure reporters explicitly:

// playwright.config.ts — reporters that behave in CI
export default defineConfig({
  reporter: [
    ['junit', { outputFile: 'test-results/results.xml' }], // pipeline test tab
    ['html',  { open: 'never' }],                          // human-browsable artifact
    ['blob'],                                              // lets sharded runs be merged
  ],
  retries: process.env.CI ? 2 : 0,   // retry transient failures in CI only
  trace: 'on-first-retry',           // capture a trace only when a test retries
});

Azure Pipelines — a real azure-pipelines.yml

# azure-pipelines.yml
trigger: [main]

pool:
  vmImage: ubuntu-latest

steps:
  - task: NodeTool@0
    inputs: { versionSpec: '20.x' }
    displayName: 'Install Node.js'

  - script: npm ci
    displayName: 'Install dependencies'

  - script: npx playwright install --with-deps
    displayName: 'Install Playwright browsers'

  - script: npx playwright test
    displayName: 'Run Playwright tests'
    env:
      CI: 'true'   # stops the HTML reporter hanging on a headless agent

  - task: PublishTestResults@2
    condition: succeededOrFailed()
    inputs:
      testResultsFormat: 'JUnit'
      testResultsFiles: 'test-results/results.xml'
      testRunTitle: 'Playwright E2E'

  - task: PublishPipelineArtifact@1
    condition: succeededOrFailed()
    inputs:
      targetPath: 'playwright-report'
      artifact: 'playwright-report'
✓ Good practice

condition: succeededOrFailed() is deliberate — you want results and the report published especially when tests fail. Keep credentials in a variable group / secret store and inject them at runtime; never hardcode them in the YAML.

Sharding across containers, then merging one report

Split the suite across parallel jobs, have each publish its blob-report, then a dependent job merges them into a single HTML report:

jobs:
  - job: e2e
    strategy:
      matrix:
        shard-1: { shardIndex: 1 }
        shard-2: { shardIndex: 2 }
        shard-3: { shardIndex: 3 }
    steps:
      - task: NodeTool@0
        inputs: { versionSpec: '20.x' }
      - script: npm ci
      - script: npx playwright install --with-deps
      - script: npx playwright test --shard=$(shardIndex)/3
        env: { CI: 'true' }
      # each shard uploads its blob report under a shared, indexed name
      - task: PublishPipelineArtifact@1
        inputs:
          targetPath: 'blob-report'
          artifact: 'blob-report-$(shardIndex)'

  - job: merge
    dependsOn: e2e
    condition: always()   # run even if a shard failed, so you still get a report
    steps:
      - task: NodeTool@0
        inputs: { versionSpec: '20.x' }
      - script: npm ci
      - task: DownloadPipelineArtifact@2
        inputs: { path: 'all-blobs', patterns: '**/blob-report-*/**' }
      - script: npx playwright merge-reports --reporter=html ./all-blobs
        displayName: 'Merge shard reports into one HTML report'
✗ Pitfall

The most common sharding failure is "merge finds no reports." Every shard's blob artifact must follow the same naming pattern so the merge job's download can gather them all. And don't set more workers than the agent has cores — over-subscribing causes timeouts, not speed. For medium-to-large suites, 4–8 shards is a good range.

Under the hood

Each shard writes a blob report — a machine-readable event stream, not HTML — and merge-reports stitches the blobs from every shard into one HTML report; that's why the shard artifacts must share a consistent name for the merge job to gather them. Setting CI=true also flips Playwright's defaults (no reporter auto-open, retries and forbid-only honoured), which is why an unset CI variable is the usual cause of a hung reporter on a headless agent.

        if: ${{ !cancelled() }}   # keep the report even when tests fail
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 30

These are the questions Senior QA Automation / SDET loops actually ask in 2026. Each one is collapsed — read it, answer it aloud, then open it to compare. The goal is to adapt the answer to your own experience, not memorize it.

Before you start

Answer with experience, not definitions. The most common way strong candidates lose points is reciting a textbook definition instead of telling a short story — what you did, why, and what it prevented. Say the tool names, the stages, the numbers.

Q1 How does Playwright communicate with the browser differently from Selenium?+

Playwright keeps a single persistent WebSocket open to the browser and speaks its native protocol — CDP for Chromium, patched protocols for Firefox and WebKit. Selenium sends each command as an HTTP request through the W3C WebDriver protocol to a driver binary that relays it to the browser. Fewer layers means less latency per action and no separate driver to manage, which is why Playwright is faster and can wait on real browser state instead of polling.

Why they ask

It's the classic opener — it separates people who've only used the API from people who understand what's happening underneath.

Q2 Explain auto-waiting and actionability. Why does it reduce flakiness?+

Before any action, Playwright waits for the target element to pass a set of actionability checks — visible, stable (not animating), enabled, receiving events, and attached to the DOM. So click() waits for the button to actually be clickable, including waiting out a loading overlay. That removes the need for manual sleeps before most actions, and manual waits done wrong are the number-one source of flaky tests.

Why they ask

Flakiness is the biggest real-world pain in automation; they want to hear "actionability checks" and "no hard-coded sleeps," not "I add a wait."

Q3 How do you keep a suite from getting flaky?+

Wait for outcomes, not durations: use web-first assertions like expect(locator).toBeVisible() that auto-retry, and waitForResponse for a specific network call — never waitForTimeout. Keep tests isolated with their own data so order never matters. Prefer resilient, user-facing locators. In CI, allow a retry or two but treat every retried test as a defect to root-cause, not paper over.

Why they ask

It's a proxy for maturity — juniors add sleeps, seniors remove the reason the wait was needed.

Q4 What are browser contexts, and why are they useful?+

A browser context is an isolated session inside one browser instance — its own cookies, localStorage, and session state, like an incognito window that shares nothing. Contexts are cheap to create (much cheaper than launching a browser), so they let you run tests in parallel with no state leakage, and test multi-user scenarios — admin and regular user side by side — in a single test. It's also how Playwright injects saved auth to skip login.

Why they ask

It's the concept behind fast, parallel-safe execution without Selenium Grid — understanding it shows you get the isolation model.

Q5 How do you handle authentication across a large test suite?+

Log in once in a setup project, save the authenticated state to a JSON file, then have every other project reuse it — so the whole suite authenticates once instead of before every test.

// setup test: log in, then save the session
await page.context().storageState({ path: 'playwright/.auth/user.json' });

// config: every project reuses it — no test logs in again
use: { storageState: 'playwright/.auth/user.json' }

Wire it with a setup project plus dependencies, and add the .auth file to .gitignore — it's a live credential.

Why they ask

Re-logging-in per test is a top cause of slow suites; they want the storageState + setup-project pattern by name.

Q6 What are fixtures, and why use them over beforeEach?+

Fixtures are Playwright's dependency-injection system: they set up a test-scoped resource before a test and tear it down after. Built-ins include page, context, browser, and request; custom fixtures encapsulate reusable setup — an authenticated page, seeded data, an API client — and inject it only into tests that ask for it. The key advantage over beforeEach: teardown still runs even if the test fails, so resources don't leak and state doesn't bleed between tests.

Why they ask

It reveals whether you structure a real framework or just script linear tests.

Q7 Walk me through your locator strategy.+

Prefer how a user identifies an element over how it's coded: getByRole first, then getByLabel / getByPlaceholder / getByText, then getByTestId, and CSS/XPath only as a last resort. User-facing locators survive markup refactors and improve accessibility as a bonus. If a locator matches several elements, Playwright throws a strict-mode error on purpose — I scope the locator more precisely rather than silencing it with .first().

Why they ask

Locators are where flakiness is born; the ladder plus strict mode is the single clearest "modern Playwright" tell.

Q8 How do you intercept and mock network requests?+

Use page.route() to match a URL pattern, then fulfill with a custom response, modify, or abort it. It's great for forcing error states, empty states, and slow networks, and for blocking third-party scripts to speed tests up.

await page.route('**/api/price', route =>
  route.fulfill({ json: { amount: 0 } })   // force the "free" state to test the UI
);

The judgment to show: don't over-mock. Mock third-party and error paths, but if you stub your own backend everywhere you stop testing the real integration.

Why they ask

It's a native Playwright strength (Selenium needs a proxy), and the "don't over-mock" caveat separates senior from junior answers.

Q9 How does parallel execution work, and what makes a suite parallel-safe?+

Playwright runs test files in parallel across worker processes; tests within a file run in order by default. You tune worker count in config. A suite is parallel-safe when tests share no state — each creates and cleans up its own data, and none depends on another running first. Context isolation makes this natural, but test data still has to be unique so two workers don't collide.

Why they ask

"It's flaky under parallelism" is usually hidden shared state; they're checking you can reason about isolation.

Q10 How would you integrate the tests into CI/CD?+

Name the tool (Azure Pipelines or GitHub Actions) and walk the five stages: trigger on push and PR, install Node + deps + browsers (--with-deps), run the tests with CI=true, publish JUnit results and the HTML report as artifacts, and gate — a failed run blocks the merge. Record trace/screenshot/video on failure only, allow a retry or two, and shard across runners when the suite gets slow, merging the shard reports into one. Handle secrets through a secret store injected at runtime, never hardcoded.

Why they ask

Pipeline ownership is now a senior expectation and a real salary differentiator; vague answers ("we run it in Jenkins") get filtered out.

Q11 How do you test APIs with Playwright, and when would you still use Postman?+

Playwright's request fixture (APIRequestContext) makes HTTP calls without a browser, sharing config, auth state, and reporting with the UI tests — so one test can seed data via the API, drive the UI, and verify backend state via the API. I still reach for Postman for exploring an unfamiliar API, sharing collections across a team, mock servers, and contract tests. Most teams run both: Postman to explore, Playwright to regress in CI.

Why they ask

They're probing for false-dichotomy thinking; "they're complementary layers" is the answer they want.

Q12 What problem does the Page Object Model solve — and when does it become an anti-pattern?+

A Page Object gathers one page's locators and actions in a single class, so tests read cleanly and a UI change is fixed in one place instead of fifty. It becomes an anti-pattern when page objects swell into "god objects" or start holding assertions: keep actions in the page object and assertions in the test, so the test still says what it's verifying. For very stable, shared flows, fixtures often compose better than deep POM inheritance.

Why they ask

Everyone says "I use POM"; the senior signal is knowing its failure modes, not just its name.

Q13 A test only fails in CI, never locally. How do you debug it?+

Open the trace. With trace: 'on-first-retry', the failing CI run captures a full timeline — every action, DOM snapshot, network request, and console log — published as an artifact. I download it and open it with npx playwright show-trace, then step through to the exact failing action and see the DOM and network at that moment. CI-only failures are usually timing, data, or environment differences, and the trace makes which one obvious.

Why they ask

They want a real debugging workflow and to hear "Trace Viewer" and "trace on first retry," not "I add more logging."

Q14 Design a test strategy for [some system].+

This is the most common senior question — practice saying it out loud. A structured answer: start from risk (what breaks that hurts most), lean on the test pyramid (lots of fast unit and API tests, fewer broad E2E on the critical user journeys), and be explicit about what you automate versus explore manually. Then: tiers and gates (a fast smoke suite gating merges, fuller regression nightly), environments and data (seeded via API, isolated per test), a flakiness budget, and reporting/metrics (coverage of key flows, escape rate, suite runtime) — all wired into CI. Close by naming a trade-off you'd make and why.

Why they ask

It's the clearest test of judgment and communication; reciting tools instead of reasoning about risk is the common failure.

Q15 What do you deliberately not automate?+

Automate stable, high-value, high-risk paths. I hold back on one-off checks, screens still changing every sprint (the maintenance outweighs the value), pure exploratory and UX/visual judgment, and low-risk areas where a flaky, high-maintenance test would cost more than it protects. Automation is an investment; it should go where it pays back.

Why they ask

"Automate everything" is a red flag; knowing what not to automate signals you've maintained a real suite.

Q16 Where do AI tools fit, and how do you keep AI-written tests trustworthy?+

I use Copilot and the Playwright MCP server to scaffold and refactor faster — generating a first draft, extracting page objects, explaining a failure. But I verify every AI-written test the same way: I break the feature on purpose and confirm the test goes red. AI (and codegen) will over-confidently grab the first matching element and invent fragile locators, so I review the locators against the priority ladder. The reviewing is the skill — a test that only ever passes is proving nothing.

Why they ask

AI is now in every workflow; interviewers want to see you use it and guard against its failure modes — that judgment is exactly what stays valuable.

Q17 Tell me about a flaky test you fixed.+

Structure it as a short story: symptom ("passed locally, failed ~1 in 5 in CI"), root cause ("it asserted before an async call finished — a timing gap, not a real bug"), fix ("replaced the sleep with expect(locator).toBeVisible() / waitForResponse on the specific call"), and prevention ("added a lint rule against waitForTimeout and isolated the test's data"). Name the numbers and what it prevented.

Why they ask

Behavioral questions reward specifics; a concrete cause-and-fix story beats any definition.

GlossaryQuick definitions for terms that come up
Locator
A description of an element on the page (e.g. "the Sign in button"). Re-finds the element each time it's used, waiting until it's there.
Fixture
Something the test runner hands your test automatically — page (a fresh browser tab) or request (an HTTP client). Keeps tests isolated.
Assertion
A check that something is true (expect(...)). Locator assertions auto-retry for a couple of seconds; value assertions check once.
Auto-waiting
Playwright's built-in habit of waiting for elements to be ready before acting or asserting — the reason manual sleeps are rarely needed.
Actionability
The checks Playwright runs before an action: is the element visible, stable, enabled, and not covered?
Flaky test
A test that passes sometimes and fails others without the code changing — usually caused by timing/waiting done wrong.
Headless / headed
Headless = the browser runs invisibly (default, fast). Headed = you can watch it on screen.
storageState
A saved snapshot of a logged-in browser session (cookies + local/session storage), reused so tests start already authenticated.
Trace
A recorded, replayable timeline of a test run — DOM snapshots, network, console — for debugging failures after the fact.
Page Object (POM)
A class that holds one page's locators and actions in a single place, so tests read cleanly and UI changes are fixed once.
Codegen
Playwright's recorder: it watches you use the app and writes the test code, picking sensible locators.
MCP (Model Context Protocol)
A standard that lets an AI assistant use external tools. The Playwright MCP server lets Copilot drive a real browser to inspect pages and generate tests.
Agent mode
A Copilot mode where it works through multi-step tasks on its own — choosing tools, acting, and adapting — rather than just autocompleting.
CI (Continuous Integration)
The automated pipeline (GitHub Actions, Jenkins, Azure DevOps) that runs the test suite on every change.
WebDriver
The W3C-standard protocol Selenium uses to control a browser — commands sent as HTTP requests through a driver binary.
CDP (Chrome DevTools Protocol)
The browser's own low-level control protocol. Playwright speaks it (and equivalents) directly over a WebSocket, which is why it's fast and can auto-wait.
WebDriver BiDi
Selenium's newer bidirectional, WebSocket-based layer — adds native network interception and live log capture, narrowing the gap with Playwright.
Selenium Grid
Selenium's infrastructure for running tests across many machines/browsers in parallel; now Docker- and Kubernetes-native.
Newman
Postman's command-line runner. Runs a Postman collection in CI (newman run collection.json).
APIRequestContext
Playwright's built-in HTTP client, exposed via the request fixture — call APIs without a browser, sharing auth and config with UI tests.
Sharding
Splitting the test suite across several parallel runners (--shard=1/3), then merging the per-shard reports into one.
Quality gate
A pass/fail rule in the pipeline — e.g. a failing test run blocks the pull request from merging.
Agent
An AI that pursues a goal across multiple steps on its own — planning, using tools, and checking results — rather than just answering once.
Agentic loop (ReAct)
The cycle an agent runs: reason → act (call a tool) → observe the result → repeat, until a stopping condition. Each result feeds the next step, so it can self-correct.
Skill
A folder with a short instruction file (SKILL.md) that teaches the AI to do one task your team's way; the AI pulls it in when its description matches.
RAG (Retrieval-Augmented Generation)
Retrieving relevant documents from your own knowledge base and feeding them to the AI so answers are current, sourced, and grounded in your data.
Self-healing test
A test that an AI automatically updates when a locator or UI element changes, instead of failing and waiting for a manual fix.
